# Scenario workspaces: implementation notes

Introduced in **0.9.0**, the scenario workspace replaced the previous single-editor identity. Version **0.9.1** adopts the **UAG Studio** name and layered **Workspace** mark across the app and documentation; branding is not a claim of certified configuration security. The repository is now `erikgraa/uag-studio`, the npm package identifier is `uag-studio`, and the public address is `uagstudio.graa.dev`. Repository/package alignment leaves the app version at **0.9.1**; previous repository URLs redirect, while older GHCR packages remain separate. Browser-local drafts and preferences do not automatically move from the old domain; see the [migration notes](technical-guide.md#moving-from-a-previous-domain). This builder release is not deployment certification or a claim of affiliation with Omnissa.

Legacy browser-storage keys and fleet-format identifiers deliberately retain their existing namespaces for compatibility. Existing same-origin drafts, appearance, output width and prior topology imports are not renamed or reset. Browser-local workspaces and preferences are origin-scoped and will not automatically follow a domain switch. Export configurations before leaving the old origin; named workspaces, fleet state and appearance require an explicit migration plan, not an assumption that a single INI export preserves everything.

## Structure

- `ScenarioApp.svelte` owns the scenario chooser, named drafts, selection and lifecycle saves. It mounts the real `App.svelte` editor directly: no precompiled review runtime or iframe dependency.
- `scenario-workspaces.ts` owns shape guards, schema-default upgrades, secret-safe snapshots and storage keys. The workspace registry is separate from the previous legacy draft, which is explicitly resumable as Single UAG and remains untouched. An unsupported registry disables writes rather than resetting it.
- `fleet.ts` owns independent UAG groups, stable shared templates, member identities, removal/Undo and authoritative source/fleet validation. `FleetTopology.svelte` is its native topology and quick inspector.
- `fleet-export.ts` checks the fleet before generating deterministic UTF-8 ZIPs. Group folders and member filenames replace whitespace with hyphens and include stable IDs so sanitization-equivalent names cannot collide. INI paths contain no spaces; original group labels, configuration names and INI contents stay unchanged, and manifest/README file references match the exported paths. `topology.json` links identities to their member INIs; `README.txt` contains the file map and manual deployment checklist. Supported earlier scenario review manifests are imported explicitly, not silently converted from browser keys.
- `ordinary-whitespace.ts` selects normalizable fields from the genuine schema. Saved/exported snapshots normalize without replacing an actively typed model. Passwords, free-form/raw content, opaque extras and untouched advanced target locators are exceptions.
- `Appearance.svelte`, `review-appearance.ts`, `appearance.css` and the HTML bootstrap resolve Original/System before initial mount. Dedicated appearance preferences are independent of configuration IDs and excluded from configuration exports.

## Saved-draft export readiness

Saved draft cards show **Ready to export** or **Needs fixes**, with blocking findings and advisory warnings counted separately. Single UAG and Web proxy use normalized checked INI/settings JSON validation. Horizon uses checked **fleet ZIP** readiness: the topology must be planned, an active UAG must remain, and all active-member and fleet-level errors must be resolved. A valid but unplanned Horizon baseline therefore says **Needs fixes** with **Topology not planned**; its existing baseline INI export remains available independently. Format labels are omitted from cards, and ready cards omit zero-blocker counts and omit the counts line entirely when there are no warnings.

Single UAG and Web proxy card names append the configured appliance hostname (`uagName`) when nonblank, not the deployment VM name or vCenter server. This is a display-only suffix: persisted draft names are not renamed, missing hostnames are not invented, and Horizon card names stay unchanged. Long names wrap rather than truncate.

Warnings alone do not block export. Counts are read-only calculations from the actual saved configuration and fleet, not cached certifications or invented deployment values. Secret omission, unsupported-storage write protection and raw locator spelling remain unchanged. New-scenario cards still create blank/default workspaces and do not show saved-draft status. Export readiness does not verify live deployment, networking, security, certificates or failover.

## Shared versus individual

A **UAG group** is a Studio configuration grouping, not an inferred Horizon pod or Cloud Pod Architecture site. Groups can be named by site (for example, “London”), but one site may contain multiple pods or UAG groups. Existing draft labels and topology-format identifiers remain unchanged. For deployment architecture, consult [Horizon Architecture](https://techzone.omnissa.com/resource/horizon-8-architecture) on Omnissa Tech Zone.

Fresh Horizon starts with one genuinely blank/default appliance and the Horizon service selected, not seeded deployment values. The operator must fill or import a configuration that passes source validation before unlocking topology and using it as the shared baseline. “Continue to fleet topology” is in the top workspace bar; after unlocking, it becomes “Save & return to topology.” This opens or updates a plan, not a deployment. Example addresses used in automated review fixtures are synthetic test data, not application defaults.

Source images require an actual filename before the platform's supported extension, not just `.ova` or `.vhdx` at the end of a directory or URL. vSphere continues to accept named local/UNC OVA paths and HTTP(S) OVA URLs; Hyper-V continues to require local VHDX paths. Invalid imported source strings stay available for correction.

An incomplete first Horizon baseline shows an amber prerequisite warning directly below the workspace/topology actions, before you try to continue. It is linked to the Continue action for assistive technology and becomes normal next-step guidance when configuration validation passes and Horizon remains enabled. The existing blocking topology guard still applies. Clicking Continue while the baseline is incomplete focuses that prominent warning without adding a duplicate click-time message.

Parseable vSphere locators require a username, vCenter FQDN/server address and compute inventory path in the full editor, initial Horizon baseline and checked fleet exports; blank usernames/server addresses and blank or slash/whitespace-only paths are blocking and a separate VM folder does not satisfy them. Encoded paths and imported spelling remain unchanged, and opaque advanced locators are not reinterpreted. DNS and NTP validation is shared with standalone workspaces: one distinct valid server produces a field-linked advisory, not an export blocker. NTP counts primary and fallback servers together using existing equivalence rules; multiple addresses alone do not prove independent redundancy. Missing, invalid and duplicate-server findings remain separate.

Applicable static IPv4 defaults require the gateway to be in NIC0's subnet and different from the NIC0 appliance address. The collision is a blocking, field-linked builder error in the full editor and fleet validation/checked export, not an automatic value rewrite. DHCP/IPv6-only and managed Azure fields are not checked as active static IPv4 settings.

The topology uses decorative, theme-aware icons alongside the existing labels: the Studio mark for each UAG, a server stack for Connection Servers, and a monitor for Horizon clients. Icons do not replace names, address details, or keyboard-operable selection controls. A green checked-box status says **Configuration ready** when no blocking configuration errors remain; a red warning icon and count mark blocking errors, which link to the affected appliance using its INI `name` (VM name), falling back to `uagName` and then the member ID. These are read-only validation indicators, not deployment certification.

A compact, read-only **Fleet overview** above the UAG groups shows Horizon clients, group boundaries, enabled supported HA VIPs, INI appliance names and every configured Connection Server destination, including individual overrides. It omits addresses, HA IDs, configuration details and validation badges, remains visible when individual UAG groups collapse, and can be scrolled horizontally on narrow screens. The overview itself starts expanded and can independently be collapsed using its keyboard-accessible heading; reopening redraws its connectors without changing configuration. Identical configured destination strings share one endpoint; different imported spellings remain distinct and unchanged. Unknown destinations do not imply a shared server. Address, appliance-name and VIP/appliance collision messages identify the conflicting UAG by its INI `name` (with a member ID to disambiguate duplicate names), not its OS `uagName`; an absent INI name falls back to the member ID. This is a conceptual XML API view, not discovery of pods, server pools, external load balancers or display-protocol routing. A **Client-facing LB** diagram toggle adds a dotted **Hypothetical** box before the UAG groups. Each configured Connection Server endpoint has an independent **LB / pool** switch: enabling it depicts that endpoint as its own dotted hypothetical LB feeding a **1–N Connection Server pool with unknown members**, rather than combining all destinations behind one shared backend LB. Selecting any backend LB / pool shows a contextual **Cloud Pod Architecture (CPA)** note: these pools could belong to federated Horizon pods, but an LB alone does not establish CPA. Pod membership, federation, global entitlements and inter-pod connectivity are not configured or verified. This note stays hidden for direct endpoints or a client-facing LB alone. Unselected nodes remain configured endpoints; their URLs do not prove whether they represent one server or a load-balanced pool. Options follow exact configured destination strings, including individual overrides and distinct imported spellings; missing destinations have no pool switch. These are temporary visual placement examples only: they do not establish server-pool membership, invent connections to unused destinations, configure routing or health checks/persistence, alter UAG URLs, affect validation/exports or get saved into configuration.

UAG groups have stable theme-aware accent borders and keyboard-operable collapsible headings. Their appliance counts and validation statuses remain visible when collapsed. The bottom blocking panel appears only when there are errors and uses neutral surfaces with restrained warning accents; selected-appliance errors also appear in its settings pane, with IP conflicts associated with the affected address inputs. NIC0 IPv6 editing appears only after an active appliance has a nonempty IPv6 address in its full configuration, and still respects field availability. New UAG groups start with blank network addresses, IPv4 netmasks, IPv6 prefix/gateway, default gateway, DNS/search domains, static routes and custom network overrides, including hidden NIC settings. They do not inherit another group's subnet anchors. After configuring the new group's first UAG, subsequent UAGs share that group's network settings while retaining blank individual addresses.

The fleet workspace has a bounded, centered width; overview columns and backend nodes stay compact rather than stretching across wide screens. Smaller gaps and node padding retain readable labels and measured connectors. HA DNS guidance sits below the backend diagram rather than stretching its VIP node. The overview scrolls internally if its optional LB columns cannot fit.

The shared Connection Server URL is edited only in the UAG group, not repeated as an editable selected-appliance field. The selected pane retains a clearly labelled destination field for explicit individual overrides or differing retained destinations; hiding a shared field does not rewrite any configuration. The **Full UAG configuration editor** action opens all settings without changing them. Blocking findings in the topology and selected-UAG pane open the affected appliance's full editor at the finding's section, then scroll to and focus its specific field. The full editor places **Validation & lint** below the current section's configuration fields, with a bounded scrollable findings list. Compact readiness/advisory and section counts stay above the fields and open and focus that panel; inline errors, collapse and jump-to-field actions are retained. An enabled group-level XML API VIP is drawn once, with connections fanning out to its members; shared backend connections converge on one Connection Server box per group. Individual overrides and differing imported destinations retain separate labelled branches. Routes adapt when cards resize or wrap; native HA still covers XML API traffic, not direct display-protocol endpoints. Its diagram is labelled **UAG High Availability**, with the XML API VIP scope retained underneath. Client DNS must match the entry-point design: for direct access, resolve the client-facing hostname to the reachable group VIP or its public/NAT address; with an external load balancer, resolve it to the frontend; with health-aware DNS/GSLB, follow that routing design. Neither a direct VIP mapping nor a particular DNS record type is a blanket requirement. Verify client DNS resolution and certificate coverage before deployment. Studio does not provision or verify DNS or certificates.

Active supported native HA groups must use unique numeric Group IDs across this topology, even across different NIC0 subnets. VIPs must not collide with another active HA VIP or appliance address. These checks preserve imported values and exclude removed, disabled and unsupported HA groups.

Add, remove, Undo and download actions retain their text labels alongside decorative icons. **Download fleet configuration** still creates the validated group-folder ZIP and remains disabled until blocking errors are resolved. Removing a UAG or UAG group requires confirmation, with Cancel focused first and Escape available. Group confirmation includes its active UAG count. Removal excludes members from exports without deleting configurations or touching live infrastructure; Undo restores retained settings.

Group destinations propagate to followers unless an appliance has an explicit destination override. Names, supported addresses and appliance-specific resource identity remain individual. Template-owner and group edits reapply shared fields. The full editor explains this to template followers; moving a member requires explicit adoption confirmation. Removing the template owner does not delete the shared snapshot. Export omits removed members/groups and clears a dangling exported owner ID; Undo retains their in-memory configurations.

Native HA is actual supported configuration generation, not planning metadata. Inconsistent member/template HA values block checked fleet export without rewriting imported values. Azure HA is unavailable. VIP ownership, subnet availability, L2, certificates and live failover still require operator verification. Only documented NIC0 IPv6 fields are exposed; NIC1/2 IPv6 keys are not invented.

## Azure and TLS evidence boundary

The supplied `uag1-basic.ini` and `uag12-azure.ini` establish INI support for `[General] honorCipherOrder`; the builder default is true and explicit false survives import, legacy promotion and export. It is intentionally INI-only: a supported admin-settings JSON mapping was not established.

The inspected Azure script uses indexed subnet, NSG and public-IP resource names. Applicable subnets are required by **Studio safety policy**, not claimed vendor-mandatory: the supplied script otherwise chooses the first VNet subnet. NSGs are optional. Public-IP resource-group and virtual-network resource-group fields fall back to the VM deployment resource group when blank. The public-IP group applies only when NIC0's existing Public IP resource name is set. The sample's `isVNetInDifferentResourceGroup` flag is not read by the supplied scripts, so fresh generation does not add it; imported opaque compatibility data is retained. No Azure lookup, resource creation or vendor-script execution is performed by the builder.

Newly recognized INI extras are promoted before defaults, with explicit known values taking precedence. Unknown entries keep their spelling. Static source inspection and automated/browser checks do not establish actual Azure deployment coverage.

## Storage and output cautions

The header has one **Save & return** action, with a teal return/check icon. It saves the current workspace and opens the chooser; selecting the brand does the same. New workspaces are created only from the chooser’s scenario cards, not by a duplicate header action. Existing write-failure notices and memory-only drafts remain visible. Saved drafts use matching scenario accents and explicit type labels/icons: purple for Single UAG, teal for Horizon, and amber for Web proxy. Color supplements the labels rather than replacing them.

The chooser’s × button removes one named workspace after confirmation. **Clear all drafts** appears beside the saved-drafts heading when drafts exist; its confirmation states the count and removes all listed configurations, fleet plans and memory-only imports. Export anything needed first: removal cannot be undone. Cancel or Escape keeps every draft; a failed storage write also keeps them and reports an accessible error. Deletion writes the secret-safe registry successfully before updating memory, never calls `localStorage.clear()`, and leaves the original legacy draft, appearance and unrelated storage untouched. With an unsupported registry, only newly created session-only workspaces can be removed; existing storage is never rewritten. Successful deletion focuses the chooser heading. Workspace action messages reset when changing scenarios, while browser-storage warnings stay visible independently.

The landing footer displays the builder version from package metadata and links to the source repository and Omnissa, alongside the independent-community disclaimer. The header spells out Unified Access Gateway for newcomers; compact layouts retain the UAG Studio name.

Appearance uses palette swatches and native System / Light / Dark radio choices. Arrow keys select within each group; Escape returns focus to the toggle. System follows live device-theme changes; explicit Light and Dark remain independent of the device and remembered palette.

Recognized passwords are omitted from physical persistence and fleet bundles, not encrypted or backed up. Credential-bearing advanced target locators remain exact and can contain secrets. Unsupported/raw imports remain in memory; only metadata is saved because unknown secret formats cannot be safely redacted. Review settings and supply credentials securely before manual deployment. Existing certificate-export policy continues to apply.

## Validation

Run `npm run check`, `npm test` and `npm run build`. Source coverage includes real-schema Azure/TLS upgrades, whitespace exceptions, appearance, fleet template/identity/removal/Undo, NIC/subnet/collision/HA checks, ZIP linkage/import compatibility, storage shape guards and server-rendered accessible topology structure. Real-browser review evidence additionally inspects actual downloaded files and native keyboard/mouse interactions; it is not infrastructure verification.
