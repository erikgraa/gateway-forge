# 🗺️ UAG Foundry roadmap

This roadmap highlights current priorities and longer-running work. It is directional rather than a release commitment: items may be reprioritized as UAG guidance and project needs evolve.

## 📍 Current state — 0.8.7

- **Included in 0.8.7:** quieter target/release/platform hierarchy, contextual section and deployment-risk disclosures, reduced duplicate guidance and fixed configuration-preview reopening. Configuration generation and vendor mappings are unchanged. Tracked in [#151](https://github.com/erikgraa/uag-foundry/issues/151); targeted responsive checks do not complete the mobile-workflow priority below.
- **Included in 0.8.6:** Horizon response security-header rows with required name/value fields, no seeded examples, retained raw-import/draft compatibility and unchanged INI-only output.

- **Implemented:** wider/collapsible output, artifact tabs and adjustable divider; HA fields, standalone-first SEG, independent JWT profiles, repeatable OIDC providers, Horizon authentication prerequisites/security-header serialization and distinct platform controls. The output/configuration work is merged in [#147](https://github.com/erikgraa/uag-foundry/pull/147) and [#148](https://github.com/erikgraa/uag-foundry/pull/148).
- **Included in 0.8.5:** all OIDC providers grouped in one enabled box without changing the vendor's unnumbered-first INI contract, and source-backed same-name VM replacement warnings for all five platforms in the workspace and generated PowerShell/Docs. See [CHANGELOG.md](CHANGELOG.md) for the complete changes since 0.8.0.
- **Completed tracking:** Hyper-V support ([#139](https://github.com/erikgraa/uag-foundry/issues/139)) and native HA/VIP configuration ([#145](https://github.com/erikgraa/uag-foundry/issues/145)) are implemented and removed from pending roadmap items. The [technical guide](docs/technical-guide.md#deployment-support-and-test-status) retains scoped deployment evidence and specific untested scenarios; issue closure does not imply blanket platform or failover certification.
- **Still unverified:** appliance-export fidelity, live SEG/JWT workflows and full mobile configure/import/export workflows. Synthetic tests and targeted desktop/tablet/phone layout checks do not close these priorities. Desktop packaging, deployment-time secrets, PowerCLI/API deployment, Intelligence and robust schema-diff automation remain future work.

## 🚀 Near term

- 🌓 **In progress — system-theme defaults and three palettes.** Default to the Original purple palette and the operating system/browser's preferred color scheme. Offer Harbor and Warm slate independently of System/Light/Dark; remember explicit overrides, respond to live system changes in System mode, and apply the appearance immediately to every editor. Tracked as part of the redesign in [#156](https://github.com/erikgraa/uag-foundry/issues/156). Source integration is underway; this is not a shipped-release claim.
- **Included in 0.9.0:** UAG Foundry identity, native Single UAG / Horizon UAG topology / Web proxy workspaces, named drafts and confirmed bulk deletion, independent palettes/themes, stable Horizon group templates and individual identities, Remove/Undo and checked grouped fleet downloads. Input, Azure networking and TLS refinements accompany a shorter README and linked technical guide. Tracked in [#156](https://github.com/erikgraa/uag-foundry/issues/156). UAG groups are not Horizon pods; protocol routing, affinity, endpoints, external load-balancer presets and live HA/failover still require source/lab verification. Automated and targeted layout checks do not complete the mobile-workflow priority below.
- 🔎 **Planned — audit paired JSON and INI exports against the Foundry schema.** Await operator-provided, sanitized exports from the same UAG configuration, with the UAG version, export method and vendor deployment-package version identified where available. Track baseline/default mapping in [#144](https://github.com/erikgraa/uag-foundry/issues/144) and importer/round-trip evidence in [#146](https://github.com/erikgraa/uag-foundry/issues/146). Compare field coverage, naming, types and import/export behavior without assuming the two formats have identical schemas; distinguish deployment file paths from embedded JSON content. Specifically audit SSH public keys and trusted CA certificates against existing Foundry support and authoritative vendor sources, then add confirmed missing mappings/fields and regression fixtures. Remove passwords, private keys, tokens and environment-identifying data before sharing; use synthetic replacement content where needed.
- 🧪 **Planned — add Pester-based UAG functional verification.** Develop high-level, configuration-driven checks against deployed UAGs, with explicit opt-in execution in a lab or other approved test environment. Detailed coverage will be defined before implementation.
- 🔐 **Planned — add a deployment-time secret wrapper.** Resolve credentials from an operator-selected secret-management provider on the deployment host, keeping the source INI passwordless and secret values out of the browser. Inject credentials into an isolated per-run temporary INI with restrictive permissions; invoke the vendor script against that copy rather than modifying/restoring the original. Fail clearly on missing secrets, verify locator handling against the deployed tool version, avoid secret-bearing logs, and clean up in `finally` on success or failure. Account for credentials exposed through vendor process arguments/logs and interrupted cleanup; deletion is not guaranteed secure erasure. Test successful deployment, missing credentials and failure cleanup before claiming unattended support. Build on the completed provider-design groundwork in [#58](https://github.com/erikgraa/uag-foundry/issues/58); provider selection and this wrapper remain unimplemented.

### 🔥 High priority

- 📱 **Planned — support smartphones and tablets.** Make the configuration builder usable on phone and tablet screens in portrait and landscape, with touch-friendly controls, responsive navigation/forms, and accessible topology, template previews and output panels. Verify the complete configure/import/export workflow on mobile browsers; mobile support is not yet validated.
- 🧠 **Planned — add Workspace ONE Intelligence support.** Verify `[WorkspaceOneIntelligenceSettings1]` and its supported keys, version/platform availability and JSON mapping against authoritative sources before adding UI, validation, import/export, topology representation and regression coverage. This integration is not currently implemented.
- ✉️ **Planned — verify SEG interoperability and deployment-package coverage.** Standalone-first `[AirwatchSecureEmailGateway]` configuration, validation and synthetic round trips are implemented. Obtain release-specific exports and verify UEM interoperability, wrapper credentials and shared/standalone behavior before claiming operational support. Baseline/schema export evidence is tracked in [#144](https://github.com/erikgraa/uag-foundry/issues/144); that investigation does not establish live SEG interoperability.
- 🔑 **Planned — verify JWT appliance exports and signing workflows.** Independent JWT consumer/producer profiles, source-backed INI and representable JSON mappings, validation and synthetic round trips are implemented. Verify release-specific exports, local key materialization and live signing/encryption workflows before claiming deployment certification. Importer/round-trip export evidence is tracked in [#146](https://github.com/erikgraa/uag-foundry/issues/146); that investigation does not establish live signing/encryption support.

## 🔭 Future goals

- 🧭 **Future goal — add pod-aware Horizon topology planning.** Represent Horizon pods, sites and Connection Server pools explicitly, and map UAG UAG groups to them rather than treating a UAG group as a pod. Account for Cloud Pod Architecture and global entitlements where applicable. Show shared client hostnames, DNS/GSLB or external load-balancer entry points, and per-group native HA VIPs while distinguishing XML API routing from per-UAG display-protocol endpoints. Verify supported routing, health checks, persistence and failover against authoritative guidance and lab evidence before adding presets or support claims. This is planning scope, not automated provisioning of pods, federation, DNS or load balancers.
- ☁️ **Investigative — determine UAG Azure deployment compatibility with Azure Local.** Track in [#153](https://github.com/erikgraa/uag-foundry/issues/153). Compare the vendor script's Azure cloud resource/API assumptions with Azure Local and Azure Arc VM management, including image, storage, networking, identity and resource-provider requirements; verify release-specific Omnissa support separately from technical feasibility. Consider direct Hyper-V deployment as a distinct possible route, not equivalent to Arc-managed VM creation. Record a source-backed conclusion and remaining operator-run lab prerequisites before any support claim or separately scoped implementation. The current Azure option does not imply Azure Local support; this is tracking only, not lab execution or certification.
- 🖥️ **Future goal — offer a standalone desktop app and automated releases.** Evaluate a Windows-first Tauri/Rust shell around the existing Svelte editor, sharing schema, validation and import/export/output-generation code with the website. Explore offline packaging and native configuration Open/Save dialogs; document WebView2 requirements and assess other platforms later. Reuse frontend CI checks, add Rust/package verification, and publish versioned installers/archives to GitHub Releases with release notes and `SHA256SUMS.txt` calculated from final artifacts after signing where configured. Keep web/desktop versions aligned; decide signing and update channels separately. The reviewed desktop mockup is illustrative only; no native app or desktop release pipeline is implemented. Track scope and acceptance criteria in [#142](https://github.com/erikgraa/uag-foundry/issues/142).
- 🚀 **Investigative — rewrite `uagdeploy` with PowerCLI bootstrap and API-based configuration.** Explore a PowerShell deployment path using vSphere PowerCLI rather than requiring `ovftool`. Validate whether `Import-VApp` and vSphere APIs can import UAG, map its networks and supply the minimal bootstrap properties needed for networking and admin access. Investigate applying service configuration after authenticated API readiness through the UAG settings PUT API rather than injecting the full configuration through OVF properties. Require trusted HTTPS reachability to the management API on port 9443, secure runtime authentication and certificate/secret materialization; the operator need not be on the same subnet if routing and firewall policy permit access. Include structured, redacted stage/error logging and post-configuration read-back verification, with functional checks aligned to the planned Pester work. Verify release-specific payload mappings and update semantics before implementation; current Foundry JSON is not a verified drop-in API request. PowerCLI bootstrap feasibility and this two-stage deployment path are not verified or supported today.
- 🔑 **Future goal — integrate secrets and PKI providers.** The [provider integration design](docs/secret-pki-provider-design.md), threat model and dormant contracts are complete ([#58](https://github.com/erikgraa/uag-foundry/issues/58), closed for that discovery scope). Actual provider adapters and runtime integration remain future work; follow the design's milestone gates before enabling them. The default workflow remains browser-only and offline-capable.
- 🤖 **Future goal — automate robust UAG schema/key diff detection.** Layer source-aware detection of new, removed, and renamed keys onto the existing weekly lifecycle workflow, compare authoritative schemas and `since`/`until` version gates, fail explicitly on parsing or availability errors, and deduplicate tracking issues. Record snapshot/source provenance and confidence, with fixture tests for parser and comparison behavior. ([#92](https://github.com/erikgraa/uag-foundry/issues/92))

## 🏷️ Status and contribution conventions

- 📌 **Planned:** accepted for the roadmap but not actively being implemented.
- 🔭 **Future goal:** valuable work that needs discovery, design, or prerequisites before it is ready for implementation.
- 🔎 **Investigative:** a feasibility question that must be validated before an implementation or support claim is made.
- 🚧 **In progress:** implementation is underway, usually linked to an issue or pull request.
- ✅ **Done:** the work has shipped and supporting documentation and tests are complete where applicable.

Open an issue to propose a roadmap item or change. Each implementation should link to its tracking issue, update the roadmap when its status changes, and include tests for behavior changes.
